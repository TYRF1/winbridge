# WinBridge v0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship v0.1 of WinBridge: a host-native Linux CLI that installs, launches, verifies, updates, exposes folders to, and cleanly removes any Windows Tauri/WebView2 app under a pinned Wine runner.

**Architecture:** A Typer CLI calls core services behind two internal protocols: a Wine backend (Bottles later) and a desktop adapter (Hyprland/X11). State is XDG-scoped; every app has a versioned TOML profile generated by zero-touch setup; runners and the WebView2 payload come from an embedded, checksum-pinned catalog.

**Tech Stack:** Python 3.11+, uv, Typer, Rich, tomli-w, Pillow, pytest, ruff, mypy.

**Spec:** `docs/design.md`

**Status:** implemented, final-review clean, and merged to `main`. The manual
release checklist has not been executed.

## Global Constraints

- Sandbox: run every plan command through `scripts/sandbox` (e.g. `scripts/sandbox uv run pytest -q`). Plan commands show the inner command; git runs on the host in the worktree.
- Python 3.11+; dependencies limited to Typer, Rich, `tomli-w`, Pillow; dev: pytest, ruff, mypy.
- Linux only. Host-native CLI; never a Flatpak. Never run anything as root.
- All state under XDG: `~/.config/winbridge/` and `~/.local/share/winbridge/`.
- Profile schema is `1`, additive changes only; unknown keys survive rewrites; backup before migration.
- Default runner is `soda@11.0-10`; v0.1 executes wine-kind runners only, via the runner's `bin/wine`.
- WebView2 is installed **before** the app, silently, and detected in both 32- and 64-bit registry views; the checksum-pinned catalog payload is the default, with `--webview2=latest` opt-in experimental.
- Wine's `dosdevices/z:` host-root link is removed at prefix creation; only `expose` links host folders, and `--keep-z-drive` is the explicit exception.
- `run` never kills a running app; only `run --restart` does. Setup/verify/update kill because they own the prefix.
- Desktop ids are stored bare (`winbridge-<id>`); the launcher has no scheme `MimeType`; the scheme handler is a separate `NoDisplay` entry; `Exec` backslashes are doubled.
- `verify` checks render only and prints "cursor not checked".
- Verify timeout `300 s`; installer quiet timeout `900 s`; settle window `5 s`.
- Exit codes: `0` success, `1` failure, `2` usage, `3` unsupported environment, `4` verify failed.
- No `shell=True`; every subprocess receives an argument list.
- No vendor names, binaries, installers, screenshots, or app-specific profiles in the repo.
- MIT.

## Review Focus

These are the five inputs most likely to hurt a real user; each is pinned by a test in the task named.

1. Windows paths with spaces, backslashes, and `%` in `.desktop` `Exec` — must parse under GLib or the launcher silently fails. (Task 9)
2. `~/.config/omarchy/shell.json` rewrites — unrelated bar widgets, themes, and unknown keys must survive; a bad write breaks the whole bar. (Task 10)
3. Registry exports with quoted paths, escaped backslashes, and separate 32/64-bit views — misparsing loses the exe, the scheme, or the WebView2 version. (Task 8)
4. Installers that exit before their child processes finish, or ignore silent flags — setup must wait for quiescence and fail with evidence. (Task 7)
5. An all-white window that is not blank — the verify heuristic must not pass a wedged WebView2. (Task 17)
6. A pin click while the app is running — `run` must not kill unsaved work; only `--restart` may. (Task 11)
